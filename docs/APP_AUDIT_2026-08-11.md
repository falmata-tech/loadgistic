# Loadgistic release application audit — 2026-08-11

## Scope

This audit covers the current supply-only product at desktop and phone sizes:

- anonymous Truck Market, Daily Featured Transporters, Track, About, login, signup, and transporter microsites;
- self-managed and company Driver capacity, Tracking, verification, support, and account workflows;
- fleet transporter Home, Fleet, Tracking, public presentation, verification, support, and account workflows;
- administrator Operations, featured scheduling, verification, ratings, billing, applications, and support;
- support-agent conversation workflows and limited-access workspace behavior;
- production build, PWA shell, navigation, public projection, deterministic fixtures, dense records, maps, forms, dialogs, and responsive layout.
- keyboard and focus behavior, landmarks and accessible names, labels and announcements, contrast and non-color state, touch targets, reduced motion, and 200% zoom/reflow.

The audit is governed by `FEAT-UIX-001`, uses real clicks and state assertions in addition to screenshots, and does not count retired Business, demand, Partners, Provider Market, Area Market, future-trip, Busy, or contract-work paths as coverage.

## Production-readiness and scale follow-up — 2026-08-15

This follow-up audits the current release candidate as a marketplace expected to
grow to thousands of providers and trucks. It distinguishes locally verified
behavior from infrastructure that is still required before public production.

### Scale baseline

The disposable audit created 500 transporters and 5,000 additional current
trucks in `/tmp`. On the audit machine, after warm-up:

- first cached 14-record page: 22.05 ms;
- filtered Empty cargo-van page: 32.94 ms;
- first response projection: 51,621 bytes;
- ten sequential pages: 140 records and 505,340 bytes;
- nine subsequent cursor pages: 20.91–23.41 ms each.

These measurements prove bounded local SQLite page behavior, not production
capacity. They do not validate concurrent users, Netlify cold starts, network
latency, Postgres RLS/RPC cost, storage, email, Realtime, or map-tile capacity.
Production load tests must run against an isolated Supabase/Netlify staging
environment with owner approval and provider quotas.

### Release blockers

1. Supabase/Postgres repository and health adapter with RLS/RPC parity.
2. Supabase Auth cookie-based SSR integration, Google OAuth, role/profile link,
   account migration policy, and negative authorization tests.
3. Shared rate limiting and bot protection.
4. Supabase private Storage bucket provisioning plus scanner/quarantine.
5. Viewport-scoped PostGIS market queries and bounded clusters.
6. Managed email, authorized Realtime/polling fallback, retention jobs, and
   webhook authentication.
7. Staging migrations 001–032, backup/restore rehearsal, monitoring, production
   tile provider, load test, and rollback drill.

`npm run launch:check` is intentionally red until these controls exist. A local
container with mounted SQLite remains a controlled demonstration target only;
it is not the Netlify production architecture.

### Proposed commit sequence for the current dirty worktree

1. Product contracts and operational documentation.
2. Brand, PWA, public shell, accessibility, and responsive presentation.
3. Public capacity geography, matching, demo supply, and performance controls.
4. Daily Featured Transporters, sponsors, and transporter microsites.
5. Provider workspace, Fleet/Driver verification, and provider-owned Tracking.
6. Private capacity sharing, email OTP/session controls, and Assisted matching.
7. Production hardening, legacy-route cleanup, CI, migrations, and deployment handoff.

Shared monoliths such as `repository.js`, `db.js`, `globals.css`, and broad E2E
files contain changes from several concerns. They must be reviewed by hunk or
kept in one coherent release-candidate implementation commit; artificial
path-based splitting must not create non-building intermediate commits.
